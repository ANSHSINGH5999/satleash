Back up your node. Verify. Recover.

Lifeboat backs up a Lightning node's channel state to Nostr relays as encrypted events, checks that backup against the live node, and restores it from the 24-word seed, with no other secret or file.

Problem, solution, how it works

Three moves. One seed.

Problem. An LND node's channel state lives on one machine. The static channel backup that protects it is a file someone has to keep copying, and it often sits on the machine that just died. If the copy is stale or missing, the money in channels depends on peers.

Solution. Lifeboat puts every backup where a wiped node can still find it, using nothing but the 24 words you already keep, and checks that what the relays hold still matches the node.

  1. 01

    Back up

    A small daemon watches lnd's channel-backup stream. Every change is encrypted with NIP-44 (which also pads it) and published to your Nostr relays as one addressable event, so only the newest copy is kept.

  2. 02

    Derive

    The Nostr key is never stored. It is derived from your wallet seed through lnd's signer, against a point nobody knows the discrete log of. A wiped node with the same seed derives the same key.

  3. 03

    Restore

    Fetch the newest backup, hand it to lnd, then keep dialing your peers. They detect the data loss and force-close, and your channel balance lands back on-chain.

Nostr kind 30078 · NIP-44 · lnd SubscribeChannelBackups · lnd DeriveSharedKey · RestoreChannelBackups

Architecture

Where the backup lives, and how it comes back.

lnd exports its static channel backup. Lifeboat fingerprints the channel set, encrypts the backup with a key that lnd derives from your seed, and publishes it to several Nostr relays. After a disaster the same seed finds it again.

Security model

Relays are not trusted. Neither is the browser.

Each of these is enforced in code and covered by a test. Integrity does not depend on a relay behaving well; availability does, which is why Lifeboat uses several.

  • The backup key is never stored.It is re-derived from your seed through lnd's signer. Lose the machine and the seed is all you need.
  • Relays see ciphertext, not contents.NIP-44 encrypted and padded. They learn that a key publishes, when, and roughly how much, not what is inside.
  • Bad relay data is ignored.Events from other keys, wrong tags, broken signatures or corrupted content are skipped. The newest valid backup across all relays wins.
  • Least-privilege macaroons.The daemon runs read-only. The restore macaroon adds import and dial rights. lnd itself confirms that neither can spend on-chain.
  • Verify without restoring.The console fetches the backup from every relay, decrypts it and compares it with the node's current channels.
  • The console is local and guarded.Loopback only, a per-run token for anything that changes state, Host and Origin checks, and a nonce-based Content Security Policy.

Limits

What it can't do.

Lifeboat recovers money, not channels. These are the edges we know about today.

  • It closes your channels.A restore brings funds back on-chain. It does not bring channel state back.
  • Peers must be online.They are the ones who force-close. An offline peer means the money waits.
  • About 200 channels per backup.NIP-44 caps a payload at 64 KB and chunking is not built yet.
  • Relays can withhold or go stale.Publish to several. Restore takes the newest copy any relay returns.
  • Verified on regtest.Public relays got a one-shot test with a throwaway key and dummy data. Testnet and mainnet have not been tested.
  • LND only.Core Lightning and LDK use different backup formats and are not supported.

Run it

Run it yourself.

The drill needs Docker and Node. It builds a throwaway regtest network, so no real coins are involved.

Open this page with the live drill button, then visit http://127.0.0.1:8080
npm install && npm run web
Regtest playground: real channels, two relays, and the console showing live data at /console
npm run playground
Full disaster drill in the terminal
npm run demo
Bake a read-only macaroon for the daemon (needs an admin macaroon once; add --restore for a restore macaroon)
LND_CERT=<lnd dir>/tls.cert LND_MACAROON=<admin macaroon> LND_PORT=8080 npm run cli -- bake --out monitor.macaroon
Run the backup daemon against your own lnd
LND_CERT=<lnd dir>/tls.cert LND_MACAROON=monitor.macaroon RELAYS=wss://relay-one.example,wss://relay-two.example LND_PORT=8080 npm run daemon
Verify the backup on the relays matches your node (a restore dry run, exits 1 if not)
LND_CERT=<lnd dir>/tls.cert LND_MACAROON=monitor.macaroon RELAYS=wss://relay-one.example,wss://relay-two.example LND_PORT=8080 npm run cli -- verify
Restore on a fresh node created from the same seed
LND_CERT=<lnd dir>/tls.cert LND_MACAROON=restore.macaroon RELAYS=wss://relay-one.example,wss://relay-two.example LND_PORT=8080 npm run cli -- restore

Only regtest has been tested end to end. Do not point the daemon at a node holding funds you cannot afford to lose.
